# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A one-page personal portfolio (React + TypeScript + Vite + Tailwind CSS v4 + shadcn/ui). Deployed to Netlify via continuous deployment from the `main` branch on GitHub.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — `tsc -b && vite build`; type-checks then produces the production bundle in `dist/`. **This is the exact command Netlify runs on deploy** — a TypeScript error here will block the live deploy even though `npm run dev` happily ignores type errors. Always run this before pushing.
- `npm run preview` — serves the built `dist/` output locally. This is the only way to see the *actual* production build (minified, no HMR) rather than the dev server; use it to verify a change before trusting it will look right once deployed.
- `npm run lint` — runs ESLint (`eslint.config.js`, flat config: `js.configs.recommended` + `typescript-eslint` recommended + `react-hooks` + `react-refresh`).
- There is no test suite/runner configured in this repo (no `test` script, no vitest/jest dependency).

## Architecture

### Everything lives in `src/App.tsx`

There is no router and no CMS/backend — the entire site (profile dialog, tab bar, tab content, lightbox) is one component tree in `src/App.tsx`. The content itself (all images/videos/audio/links per tab) is a single hardcoded literal array near the top of that file:

```ts
const tabs: Tab[] = [ { id, label, images: MediaItem[], videos: MediaItem[], audios: MediaItem[], links: LinkItem[], youtubeVideos: YoutubeItem[] }, ... ]
```

- The tab bar is generated by mapping over `tabs`; the active tab is tracked via `useState` (`activeTab`, defaulting to `tabs[0].id`) — **array order determines both the visible tab order and which tab is shown by default on load.**
- Each tab can independently hold any mix of images, local videos, local audio, external `links` (title + href + description, rendered as a card), and `youtubeVideos` (rendered as a static thumbnail from `img.youtube.com/vi/<id>/hqdefault.jpg` that links out to the real YouTube page — **not** an embedded `<iframe>` player; iframe playback was tried and reverted because it wasn't reliable).
- Adding content = editing this array directly and dropping the referenced file into `public/`. There is no upload mechanism.
- A tab is only "commented out" (hidden but ready) by wrapping its object literal in `/* ... */` inside the array — this is the established convention in this codebase for content that's prepared but not yet meant to be public.

### Media assets are served from `public/`, not imported

Images/videos/audio are referenced with root-relative paths (`/images/foo.jpg`, `/videos/foo.mp4`, `/sound/foo.mp3`) pointing into `public/images/`, `public/videos/`, `public/sound/`. `src/assets/` exists but is empty/unused (an earlier version imported images from there; everything was migrated to `public/`).

**Case sensitivity gotcha:** Windows (dev) is case-insensitive for file paths; Netlify's Linux-based hosting is not. A path/filename mismatch that works fine in `npm run dev` can silently 404 in production. Some filenames also contain spaces — this works but should be kept consistent with the literal filename in `public/`.

### `<video>` fullscreen requires an explicit CSS override

Local video previews are shown as square crops (`size-64 object-cover`) in the grid. Browsers do **not** automatically switch back to the true aspect ratio in native fullscreen — `object-fit: cover` stays applied unless overridden. The fix in place is a Tailwind arbitrary-variant on the `<video>` className: `[&:fullscreen]:object-contain [&:-webkit-full-screen]:object-contain`. Keep this pattern for any new video rendering.

### shadcn/ui components live at the repo root, not under `src/`

`components/ui/` (containing `button.tsx`, `buttonVariants.tsx`, `dialog.tsx`) and `lib/utils.ts` (the `cn()` helper) are at the **project root**, sitting alongside `src/`. `src/App.tsx` imports them with relative paths (`../components/ui/button`, `../components/ui/dialog`).

Note: `components.json` and `tsconfig.json` both define a `@/*` → `./*` path alias (root-relative), but the codebase does not actually use it anywhere — imports are relative. Don't assume `@/...` imports work in practice without checking; follow the existing relative-import style for consistency.

### The `Dialog` component is reused for two different purposes

`components/ui/dialog.tsx` (a Radix-based wrapper) backs two distinct UI elements in `App.tsx`:
1. The profile popup (`DialogNoCloseButton`), opened via `DialogTrigger`, with `showCloseButton={false}`.
2. An image lightbox for the Visuals tab, which is **state-controlled** rather than trigger-based: clicking an image sets `selectedImage`, and the dialog's `open` prop is derived from `selectedImage !== null` (with `onOpenChange` resetting it to `null` to close). This is generic over any tab's `images` array, not hardcoded to one tab.

### Tailwind v4, config-in-CSS, and the "dark mode" quirk

There is no `tailwind.config.js`/`.ts`. Theming (colors like `chart-1`…`chart-5`, radius scale, sidebar colors) is defined entirely in `src/index.css` via `@theme inline` plus `:root` / `.dark` CSS custom properties (the standard Tailwind v4 CSS-first setup, scaffolded by shadcn).

The app never actually toggles the `.dark` class on `<html>`/`<body>` — dark appearance is instead achieved by hardcoding classes like `bg-neutral-950 text-white` directly in `App.tsx`. This means **the `:root` (light-theme) CSS variable values are the ones actually in effect**, not the `.dark` overrides, even though the page looks dark. Keep this in mind before changing anything under `--chart-*`/`--sidebar-*` etc. in `src/index.css`.

### Deployment (Netlify)

`netlify.toml` pins `command = "npm run build"` and `publish = "dist"`. This file exists because of a real incident: without it, Netlify's dashboard build settings were misconfigured (publish directory not set to `dist`), so it served the raw, unbuilt `index.html` (which points at `/src/main.tsx`, a file browsers can't execute) instead of the compiled bundle — resulting in a blank page in production despite a successful-looking build log. If a deploy ever shows a blank page again, check this first.

Deploys are triggered automatically by pushing to `main` (GitHub → Netlify continuous deployment webhook) — no manual trigger needed.
